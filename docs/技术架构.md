# 登登围棋 · 技术架构

这份文档写模块怎么分、数据怎么流、为什么这么选，不抄代码细节。App 的行为和验收标准见 [需求说明](需求说明.md)。改模块边界、数据格式或关键流程时，先改这里，再写代码（流程见 `CLAUDE.md`）。

按代码核对到：2026-10-27，提交 `3278a09` 之后的本次改动。

## 1. 模块

```
DengDengGo（App 外壳）
 ├─ GoUI ──────┬─ GoVision ─ GoCore
 │             └─ GoCore
 └─ Engine/InProcessKataGo ─ KataGoBridge（Objective-C++）─ KataGo（C++，Metal / Eigen 两个后端）
```

| 模块 | 管什么 | 不管什么 | 主要文件 |
|---|---|---|---|
| `DengDengGo/` | App 入口；创建作业本和引擎，注入给 GoUI；把 KataGo 接进来：选 GPU/CPU、读启动参数、真机自测 | 界面和规则 | `DengDengGoApp.swift`、`Engine/InProcessKataGo.swift`、`Engine/EngineSelfTest.swift`、`Engine/analysis.cfg` |
| `GoKit/GoCore` | 规则、题目模型、变化树、引擎接口、KataGo 的 JSON 协议、死活外框、给每手打分、对弈的 AI 选手和数子 | 界面、图片、文件存储；不依赖任何别的模块 | `Board`、`Position`、`Problem`、`GameTree`、`GoEngine`、`KataGoEngine`、`TsumegoFrame`、`EngineSolver` |
| `GoKit/GoVision` | 照片 → `RecognizedPage`：找棋盘图、认子、读字 | 存储、界面 | `PageOrientation`、`PageRecognizer`、`GridDetector`、`StoneClassifier`、`TextReader`、`GlyphReader`、`RecognizedPage` |
| `GoKit/GoUI` | 所有界面；摆题和做题的状态（`ProblemEditorModel`）；作业本的存取 | 直接调 KataGo：只通过 `GoEngine` 接口 | `ProblemEditorModel`、`ProblemEditorView`、`ImportViews`、`HomeworkStore`、`HomeworkViews`、`BoardView` |
| `GoKit/Tools/BoardSnapshot` | 把棋盘渲染成 PNG，没有模拟器时检查画面 | | |
| `ThirdParty/KataGo` | KataGo v1.16.4 源码里 App 用得到的部分；`eigenbackend.cpp` 改过几处，`analysis.cpp` 的 `clear_cache` 补了判空（没开 subtreeValueBias 时原来会崩），都标了“登登围棋改动” | | |
| `ThirdParty/KataGoBridge` | 在 App 进程里跑 KataGo 的 analysis 命令，把标准输入输出换成内存队列；`KataGoBackend.cpp` 在运行时转发到 Metal 或 Eigen | | |
| `ThirdParty/Eigen` | Eigen 3.4.0 头文件，CPU 后端用 | | |

依赖规则：
- GoCore 不 import 任何别的模块，也不 import SwiftUI，只用 Foundation。
- GoVision 只依赖 GoCore，以及系统的 Vision 和 CoreGraphics。
- GoUI 不知道 KataGo 怎么跑，只拿到一个 `(any GoEngine)?`。为 nil 时不打分、AI 不应。
- 测试里换成假的引擎和假的通道，不用真的 KataGo。

## 2. 核心数据

| 类型 | 在哪 | 是什么 |
|---|---|---|
| `Board` | GoCore | 9、13 或 19 路盘面，每个点黑、白或空 |
| `Point` / `Stone` | GoCore | 交叉点 (x, y)，原点在左上；黑、白 |
| `Position` | GoCore | 盘面、轮到谁、打劫禁着点、双方提子数；`playing(_:)` 按规则落子，下不了时抛出 `MoveError` |
| `Problem` | GoCore | 一道题：id、题目名、摆好的盘面、谁先下、题目类型 `ProblemGoal`、印在子上的字、印出来的区域 `BoardRegion?` |
| `ProblemGoal` | GoCore | 三种题目类型，只决定外框怎么摆 |
| `GameTree` | GoCore | 变化树。节点只追加，不移动；删除变化只是从父节点上摘掉。记着重做时走哪个分支 |
| `EngineQuery` / `EngineAnalysis` | GoCore | 发给引擎的局面：起始盘面加手顺、规则（日本 / 中国）、贴目、次数、不下的点、优先级、要不要策略网络的概率。引擎回的结果：候选手、目差、每个点归谁、每个点想下的概率（`policy`，下不了的是 −1） |
| `MoveScore` | GoCore | 一手的得分：亏几目、下在题目外面、算不出来 |
| `EngineDepth` | GoCore | 快、标准、深 = 每个局面算 100、200、400 次 |
| `AIStrength` | GoCore | 对弈时 AI 的棋力：入门、初级、全力 = 随机抽 5 个点、抽 15 个点、不抽（下最好的一手） |
| `GameCount` | GoCore | 数子结果：双方子数、贴目、死子、每个点归谁 |
| `RecognizedPage` / `RecognizedDiagram` | GoVision | 一页的识别结果：每个图的位置、棋子、棋盘边、题号、没认准的点、是否没拍全；页面的黑先白先、题型、页码 |
| `SavedProblem` | GoUI | 作业本里的一道题：`Problem`、第一次存的时间、有没有原图、是否没拍全（识别时打上，家长点“已经全了”或重拍拍全了才去掉）；拍照来的题还记着作业纸上的页码和题号（`page`、`number`），重拍时用来认出同一道；是不是例题（`isExample`，例题删不掉。以前存的例题文件里没有这一项，按题目名以“例题：”开头认） |

## 3. 关键流程

### 3.1 拍照到做题

1. `ImportControls`：系统文档扫描或相册，得到 `CGImage`。
2. `ProblemEditorModel.importPhoto` 在后台线程（`Task.detached`）先用 `PageOrientation.upright` 按文字方向把照片转正，再调 `PageRecognizer.recognize`。后面显示、裁原图都用转正后的图。
3. `show(_:from:)`：给每道题分配作业本 id，裁出原图，全部存进 `HomeworkStore`。作业本里有同一页同一题号的拍照题，就沿用它的 id 和第一次存的日期，等于覆盖（D18）。存了哪几道、换了哪几道写进 `ScannedPage.note`。一道题直接 `loadDiagram`，好几道弹出 `DiagramChooser`。选题页只在这时弹出，`ImportControls` 上没有再打开它的按钮：题都在作业本里，换题从作业本选。
4. `loadDiagram`：进入摆题模式，选“轮换”工具，标出没认准的点。
5. `switchMode(to: .solve)`：作业本里的题改过就存回去，然后 `restart()`：新建 `GameTree`，新建 `Judge`。
6. 做题时点“上一题”“下一题”：`startPreviousProblem()`、`startNextProblem()` 拿 `HomeworkStore.problem(before:)`、`problem(after:)` 给的那道，换上题目和原图，直接 `restart()`，不回摆题。

### 3.2 识别管线（GoVision）

0. **转正**（`PageOrientation`，在 `PageRecognizer` 之前单独调）：把照片缩到长边 1200，用系统文字识别读字。每行字有从左到右的走向，按字数给四个方向投票，六成以上朝一个方向就按它转正。读出的字少于 4 个时不转。
1. **灰度、墨迹和线点**：`GrayImage` 把长边缩到 2000 像素。
   - 墨迹图：用局部阈值，不怕阴影。认子、撑外框用它。
   - 线点图（`ridges`，横线、竖线各一张）：比上下（竖线看左右）两侧 `lineGap` 像素处（工作图宽度的 1/250，6～8 像素）都暗 15% 以上、并且至少暗 25 级灰度的点。找线、认子时看空点上有没有线，都用它（D19）。
2. **找棋盘图**（`GridDetector`）：
   - 棋盘图是一大片连着的长直线，文字和题号里没有长直线；
   - 先去掉杂线：几乎不和别的线交叉的长线，是书缝、页边、页码下面的横杠，会把题和隔壁页、页码连成一片（D20）。具体是：一条都不交叉、比 3 格长的；只交叉两条、比 6 格长的。格子大小按整页交叉够多的线量。细线碰到粗的棋盘边时，像素停在粗线外沿，所以顺着线再往前看 `lineGap` 像素也算交叉；
   - 棋子摆得密时长直线露不全，顺着连着的墨迹把外框撑大。每边最多撑 5 个线距，撑到上限、照片边上或离照片边不到 2 个 `lineGap` 的那边不撑；也不顺着去掉的杂线走（杂线两边各让开 1.5 个 `lineGap`）。书缝的阴影会一路连到隔壁页；
   - 试一遍“斜率 + 斜率随位置的变化”，把拍歪、书页弯曲的线拉直；
   - 外框里最外面的一条线，往两头 1～2 格处一路都是墨（5 处看 4 处以上），是穿过整个图的书缝阴影，不当棋盘线；
   - 横竖线距分开算（书页斜着拍时不一样）。两条找到的线中间按线距等分补线，被棋子挡满的行列也按线距补上；
   - 一个方向至少找到 4 条线，另一个方向 2 条也行，最后至少 4 行 4 列：反光挡住一半的图也认；
   - 每条线先按直线拟合。线露出一半以上时再按二次曲线拟合：书页卷向书缝时线会弯，中间和两头差不到半格才用。斜度和前后两条线的中位数差 0.015 以上的（被棋子挡得只露出一点，拟合歪了），按前后的斜度重新定；
   - 横线伸过最后一条竖线 0.75 格以上（平常最多伸出半格），那里还有一列，挤在书缝里找不到，按线距补上。四边都这样看，每边最多补一条；
   - 粗线是棋盘边。
3. **认子**（`StoneClassifier`）：每个交叉点看三种特征。黑子中间是实心墨；空点有网格线穿过中心；白子中间空白、外圈有轮廓。三种都不明显的点标成“没认准”。
   - 黑子要圆：中心往上下左右各 0.33 格都还是墨。书缝的阴影是窄长的一条，铅笔印比棋子小，都不算；
   - 看空点上有没有线，墨迹图和线点图有一个是线就算：手晃糊了的浅线墨迹图上没有；
   - 白子的轮廓外面就是纸；斜方向上碰到轮廓的地方，四分之三以上往外到 0.6～0.7 个线距还是墨的，是书缝那样的一大片阴影，不算白子；
   - 离去掉的杂线（书缝的阴影）不到 0.35 格的点不认黑子；轮廓要碰到四分之三以上才算白子，不然当空点、标成没认准：书页卷得厉害时阴影又黑又宽，阴影的边也会被当成轮廓；
   - 整页比一比黑子有多黑（`dropFaintBlacks`）：量离中心 0.22～0.38 格那一圈的灰度，除以周围纸的亮度。比本页黑子的中位数浅 1.6 倍以上、又超过 0.33 的，是铅笔印、橡皮屑，当空点、标成没认准。不看正中间，因为黑子上会印白色的数字。
4. **读字**（`TextReader`，系统文字识别，中英文）：页面上的黑先白先、题型关键词、题号、页码。读不出时，`GlyphReader` 把圈里的数字抠成白底黑字再读，或者按墨迹形状猜“1”。
5. **整理**：
   - 按版面格子排题号，读错的按前后题号改正。再看整页：读出的数字是按格子该有的题号的开头或结尾（10 只读出“0”），也算对得上；读出来的都对得上，或者两道一字不差、超过一半对得上，就按格子把整页补齐、改正；
   - 图最外面的一列（行），那一侧不是棋盘边、又有三分之二以上是黑子的（`clearShadowLines`），是挤在书缝阴影里的那一列，整列清空、标成没认准；
   - 比同页大多数图少一行或一列的，标成“没拍全”，从棋盘边那一侧量，补成大多数图的大小，缺的是空点；
   - 页码只看照片下面四分之一，跳过棋盘图里面的字（白子上的数字）、图左上方题号位置上的数字和圈起来的题号。题号先按位置认：灰底的圆圈在墨迹图上不一定找得到，最下面一行的题号一落进下面四分之一，就会被当成页码；
   - `RecognizedDiagram.problem(...)` 按棋盘边把图贴到 19 路棋盘对应的角或边。

### 3.3 打分（GoCore）

`EngineSolver` 有两种用法（`EngineSolver.Purpose`）：做题用下面这一整套；对弈不用外框、要分死活的子和搜索范围，见 3.5。


1. **外框**（`TsumegoFrame`）：
   - 在题目区域外面摆满两色、都活净的棋子，再按两边外框的目数定贴目（日本规则），让全盘输赢只看题目这一块。
   - 区域和外框颜色由题目类型决定，见需求说明 F7。
   - 13 路以下，或者题目超过半个棋盘时，不加外框。
2. **给一手打分**（`EngineSolver.score`，结果是 `MoveScore`）：
   - 比较下这一手之前的目差，和下这一手之后的目差，都从下这手的一方来看，黑白都一样。
   - 两次搜索各有误差，取对下棋的一方有利的那个估计。亏的目数小于 0 时算 0。
   - 下在题目区域外面，不问引擎，直接返回“在外面”。引擎出错返回“算不出来”。
   - 不判对错，也不判做没做完。界面按亏没亏过 1.5 目（`EngineSolver.tolerance`）上颜色。
3. **要分死活的子**：开头分别算“做题方先下”和“做题方停一手”，归属变化超过 0.6 的子就是要分死活的子。现在只用来限制搜索范围。
4. **搜索范围**：
   - 开头只避开离所有棋子两路以外的空点；
   - 之后双方只在要分死活的那几块棋旁边一路以内下（`EngineQuery.avoid`）。没有要紧的地方时，AI 不停一手，走一步闲棋（`EngineSolver.reply`）：先从候选里挑题目区域里亏得最少的落子；没有就挑区域里一个合法、不填自己眼的空点；都没有才停一手。为什么：真人不会在对方还在下的时候一直停，停一手会让孩子以为出错了。
5. **缓存和提前算**：
   - 按手顺缓存每个局面的分析任务。打分用到的“下之前”的局面，就是上一次替对方应手时算过的那个。
   - 轮到人下时，`prepare` 先算眼前的局面，再用低优先级（`priority = -1`）猜引擎最想下的 3 手。
   - 下了别处，`dropGuesses` 取消没用上的猜测，`KataGoEngine` 给 KataGo 发 terminate。

### 3.4 打分和 AI 陪下的状态（GoUI，`ProblemEditorModel`）

- **两个开关**：`autoScore`（AI 打分）、`autoReply`（AI 陪下），互不影响。至少开一个、有 `Judge`，才用引擎。
- **每个节点记三样东西**：
  - 得分 `scores[node]`；
  - 给人看的提示 `notes[node]`；
  - 这手是不是 AI 下的 `aiMoves`。

  悔棋、重做、切换变化时按这些配对，AI 的应手跟着人那手走。
- **执哪方**：做题时，最近一手不是 AI 下的，那一手的颜色就是人执的。对弈时看设置，见 3.5。
- **没有终点**：每一手都打分、都应。只在有一手下在题目区域外面时停下，悔掉那一手就接着来。
- **补上**：打开某个开关时，最后一手是人下的，就补上缺的分数或应手。
- **应手的停顿**：从人落子开始算，至少 0.3 秒，引擎计算和停顿同时进行。
- **切出 App**：App 离开前台时 `leaveForeground()` 取消 `work`，叫停引擎（`interrupt()`）；回到前台时 `returnToForeground()` 调 `resume()`，补上缺的分数和应手（D21）。

### 3.5 对弈

- **一个模型三种模式**：对弈是 `ProblemEditorModel` 的第三个模式 `.play`，和做题共用变化树、打分、应手、悔棋、变化那一套。
  - 对弈用一道临时的空棋盘题（`gameProblem`），不动 `problem`，也不存作业本。
  - 离开对弈时，把这一盘（变化树、`Judge`、分数、提示、哪些手是 AI 下的、数子结果）存进 `savedGame`；回到对弈原样拿回来，再 `resume()` 补上没算完的分数或 AI 的应手。只存在内存里。
  - 换棋盘大小就是开新的一盘；换执哪方只改 `playingAs`，不动变化树。
- **引擎那边**（`EngineSolver`，`purpose: .game`）：
  - 整个棋盘都是区域，不加外框，不避开任何点，不找要分死活的子；
  - 中国规则，贴 7.5；
  - 打分的算法和做题一样。
- **AI 下哪手**（`reply`）：
  1. KataGo 最好的一手是停一手，就停（做题时走闲棋，这里不走）。
  2. 全力档下 KataGo 最好的一手。
  3. 入门、初级：从 `policy > 0`、不填自己眼的点里随机抽 5 个或 15 个，下 policy 最高的那个。随机数可以给种子，测试时每次一样。
- **执哪方**：由设置 `humanColor` 决定，不看“最近一手是谁下的”。轮到 AI 的颜色、AI 陪下开着时，AI 下，所以执白时 AI 先下。
- **数子**（`EngineSolver.count`）：
  1. 用当前局面的 ownership，归对方的把握达到 0.5 的子算死子（`EngineSolver.deadOwnership`），拿不准的算活的；
  2. `Board.count(dead:)`：去掉死子，数活子，加只碰到一种颜色的空地；两种颜色都碰到的空地不算；
  3. 白方加贴目，得出 `GameCount`。

  没有引擎或者引擎出错时，界面直接用 `Board.count(dead: [])`，不判死子。数完以后落子、悔棋、切换变化都清掉结果。

### 3.6 KataGo 接入

- `KataGoEngine`（GoCore）走 KataGo 的 analysis JSON 协议，一行一个请求，按 id 对上结果，可以同时算好几个。底下的 `KataGoTransport` 只管收发行，测试里换成 `FakeTransport`。
- **叫停**：`interrupt()` 发 `terminate_all`，等着的请求都以 `EngineError.interrupted` 失败。下一个请求之前先发 `clear_cache`，丢掉 KataGo 神经网络缓存里可能在后台算坏的结果（D21）。
- `InProcessKataGo`（App 外壳）实现这个通道，调 `KataGoBridge`，在 App 进程里启动 KataGo。整个进程只启动一次，全 App 共用一个 `shared`。
- **硬件选择**：有能用的 GPU 就用 Metal；模拟器里用 Eigen（CPU），因为模拟器的虚拟 GPU 不支持 MPSGraph。启动参数 `-katagoHardware` 可以强制指定。
- **配置**：`analysis.cfg` 打包进 App；CPU 时追加线程数、批大小、NHWC 这几项设置。
- **模型**：`kata1-b18c384nbt.bin.gz`，约 98MB，不进仓库，用 `Scripts/fetch-katago-model.sh` 下载，编译时打包进 App。没有模型时 `shared` 是 nil，App 不打分。

## 4. 并发

- 全部代码按 Swift 6 严格并发编译。
- `ProblemEditorModel`、`HomeworkStore` 都在主线程（`@MainActor @Observable`），界面只读它们的属性、调它们的方法。
- `Judge` 是 actor，包着同样是 actor 的 `EngineSolver`。等引擎时不卡界面。
- 打分和应手放在一个 `work` 任务里跑。关掉开关、换模式、重新开始或 App 离开前台时取消这个任务；结果回来时要先确认当前节点没变，才写回去。
- App 外壳看 `scenePhase`：不是 `.active` 就 `leaveForeground()`，回到 `.active` 就 `returnToForeground()`。
- `EngineSolver` 碰到 `.interrupted` 的结果不留，重新算一次。这样存在别处的 `Judge`（比如离开对弈时存起来的那一盘）里被叫停的请求，回来用到时也会重算，不会当成算不出来。
- 识别在 `Task.detached(priority: .userInitiated)` 里跑。
- KataGo 的输出在它自己的线程上回调，`KataGoEngine` 内部加锁，再交给等着的 continuation。

## 5. 存储

- **位置**：`Application Support/作业本/`
  - 每道题一个 `<UUID>.json`，内容是 `SavedProblem` 的 JSON；
  - 有原图的，存一个同名的 `.jpg`（质量 0.8）；
  - `.例题已放` 是标记文件，有它就不再放例题。
- **读**：打开时读全部 JSON，读不了的跳过。原图用到时再读，读过的缓存在内存里。
- **顺序**：有两种，正好相反。一页拍照存的题共用一个时间，同一时间按题目名排（题号按数字大小）。
  - 上一题、下一题：`problem(before:)`、`problem(after:)` 按 `saved` 从早到晚，同一时间题号从小到大，按做作业的先后往下做。
  - 列表：`HomeworkStore.problems` 是上面倒过来：`saved` 从新到旧，同一时间题号从大到小。新拍的在上面好找，按天分组也就是新的一天在前。
  - 以前的版本一页的题按题号一道道存、各取各的时间，排出来也是这个顺序。
- **兼容旧数据**：`Problem` 和 `ProblemGoal` 都有自定义的 `init(from:)`：缺的字段给默认值，旧的枚举值映射到新的。
  - 以后改 `Problem` 或 `SavedProblem` 的字段，必须保证旧文件能读，并加一个像 `HomeworkTests.readsOldGoals` 那样的测试。
- **设置**：思考深度存在 `UserDefaults` 的 `engineDepth` 里，对弈的 AI 棋力存在 `aiStrength` 里（都用 `@AppStorage`）。其他开关和对弈的棋盘、执哪方不存，每次打开恢复默认。

## 6. 构建、运行和测试

- **环境**：Xcode（Swift 6）；App 要求 iPadOS 17；GoKit 能在 macOS 14 上编译和测试。
- **优化**：GoCore 和 GoVision 在 Debug 下也开 `-O`，不然打分和识别慢上百倍。
- **启动参数**：

  | 参数 | 作用 |
  |---|---|
  | `-sampleProblem` | 打开就摆上例题（UI 测试用） |
  | `-katagoHardware gpu\|cpu\|off` | 强制用 GPU 或 CPU；`off` 不用引擎、不打分 |
  | `-engineSelfTest <照片>` | 仅调试版：识别这张照片，用引擎做每道题，打印速度、正解、每手等了多久 |
  | `-engineDepth quick\|standard\|deep` | 自测用的档位 |
  | `-engineSpeedOnly` | 自测只测速度 |
  | `-engineGame` | 仅调试版：9 路上入门、初级、全力各和全力 AI 下 40 手，打印每档平均每手亏几目、每手等了多久 |
  | `-engineProblem <题号>`、`-engineVisits <次数>` | 自测只做一道题，打印每个子的归属 |
  | `-katagoConfig "k=v, k=v"` | 仅调试版：临时改 KataGo 配置 |

- **单元测试**：`cd GoKit && swift test`，包括 GoCoreTests、GoVisionTests、GoUITests 三组。
  - 引擎都用假的：`FakeTransport`、`ScriptedEngine`、`RecordingEngine`、`SampleEngine`。
  - 作业本测试各用自己的临时目录。
  - 读照片的测试只在仓库根目录有 `棋盘照片样例/` 或 `Samples/` 时跑，并且排队跑：几个测试同时用系统文字识别会卡住。用程序画图的识别测试（`RecognitionTests`）也排队跑。
- **UI 测试**：`DengDengGoUITests`，在 iPad 模拟器上跑，带 `-katagoHardware off -sampleProblem`，结果固定。检查横屏、竖屏布局和提示的位置。`-samplePhotoProblem` 摆上一道带原图、标着没拍全的题，作业本放在临时目录，不碰真的作业本。界面原则见第 8 节。
- **真机**：用 `xcodebuild` 编译，用 `xcrun devicectl device install app` 装到 iPad。命令见 README。

## 7. 架构决策

每条写当时为什么这么选、放弃了什么。推翻某条时，在原条目上注明，并加一条新的。

- **D1 全部在本机运行，不做服务端**（一期起）
  - 为什么：作业照片是孩子的个人信息；家里随时能用；不用运维。
  - 代价：模型约 98MB，App 安装包变大。
- **D2 KataGo 在 App 进程里跑**（e2f64e4、dacbb89）
  - iOS 不能起子进程，所以把 KataGo 的标准输入输出换成内存队列。
  - Metal 和 Eigen 两个后端都编进 App，运行时选：真机用 GPU，模拟器只能用 CPU。
  - Eigen 后端在苹果芯片上改过（交给 Accelerate 等），快了约 18 倍。
- **D3 用“外框 + 亏几目”衡量一手，不按题型写规则**（e2f64e4）
  - 为什么：不用知道“要吃哪块”，做活、杀棋、连接、切断都能算。
  - 用日本规则：试过中国规则，输的一方会往死棋上一直加子，挣扎二三十手。
- **D4 删掉入门判题器，只用 KataGo**（1772b4d）
  - 原来的 PDF 计划吃子、对杀用自研搜索。但它只会吃子、逃子、对杀，第 35 页第 11 题就找错了目标。
  - 删掉以后少维护一套判题逻辑。
  - 代价：没有引擎时完全不打分；模拟器上算一手要几十秒。
- **D5 题目类型只决定外框，归成三种**（1772b4d）
  - 七种题型里，很多对 KataGo 来说外框完全一样，只有提示文字不同。
  - 改成三种，每种的效果确实不同，提示按棋盘上实际发生的事说。
- **D6 一直下到结果摆在棋盘上**（46cf6d5）——已被 D12 推翻
  - 只要局面倒向做题方就判“答对了”，孩子不知道接下来怎么吃。现在要真的提掉，或者死活定下来。
  - 第一手以后限制搜索范围，不让输的一方往空地里跑。
- **D7 AI 下孩子的对手，不固定是白棋**（b1dc792）
  - 孩子可以执题目里后下的一方练习应对。
  - 按“最近一手不是 AI 下的”判断孩子执哪方，不额外加设置。
- **D8 思考深度按次数，不按时间；孩子想的时候先猜着算**（8df9aa8）
  - 按次数，同一局面每次结果一样，好测试，也好复现。
  - 等的时间靠提前算来缩短：猜中了，孩子下完马上应。
- **D9 识别用图像算法加系统文字识别，不训练模型**（b047fbe、dacbb89）
  - 印刷图对比度高，图像算法够用，好调试。
  - 难拍的照片靠样例照片逐题核对来改进。
- **D10 作业本每道题一个 JSON 文件，不用 SwiftData**（49fb293）
  - 格式简单，测试可以用临时目录；坏了一个文件，不影响别的题。
  - 旧数据兼容靠自定义解码，见第 5 节。
- **D11 作业本只存题目，不存做题过程**（49fb293）
  - 先让题目能存、能找回来。做题记录等家长中心一起做，见需求说明“还没做”。
- **D12 不判对错，只给每一手打分，没有终点**（2026-10-23）
  - 为什么：
    - “答对了”要靠一组猜测：找要分死活的子，看要吃的子提没提掉、死活定没定，再加下满 15 手也算完。这部分最容易出错，也最难解释。
    - 只给“比最好的一手亏几目”，一个口径管所有题型；自己两边下、摆变化时也能看分。
  - 放弃了什么：孩子得不到“做完了”的明确结论，要靠分数的颜色和家长来判断。
  - “AI 打分”和“AI 陪下”是两个独立开关，可以只打分不应，也可以只应不打分。
- **D13 对弈用中国规则，按按钮数子，死子交给 KataGo**（2026-10-23）
  - 为什么：孩子不会点死子；一个“结束，数子”按钮比“双方都停一手”好懂。中国规则下收单官、提死子不亏目，数子也简单。
  - 放弃了什么：KataGo 偶尔判错死活。数错了可以悔棋接着下，再数。
  - 做题照旧用日本规则（D3）。
- **D14 AI 放水用“随机抽点、挑策略最高”，不用仿人类模型**（2026-10-23）
  - 借鉴 KaTrain：每手从能下的点里随机抽几个，下 KataGo 第一感觉最想下的那个，抽得越少越弱。
  - 为什么：不加约 100MB 的模型，不多占内存；一个数就能调强弱。
  - 放弃了什么：没有仿人类模型下得像真人，偶尔有怪手。不抽填自己眼的点，免得最傻的那种。
- **D15 对弈和做题共用一个模型，切换模式不保留对局**（2026-10-23）——“不保留对局”已被 D16 推翻
  - 为什么：变化树、打分、应手、悔棋都现成，不用再写一套。
  - 放弃了什么：误点到别的模式，这盘就没了。
- **D16 切换模式保留对局，只存在内存里**（2026-10-23）
  - 为什么：下一盘要好一会儿，中途切去看题、误点模式，回来要能接着下。
  - 怎么做：离开对弈时把对局整个存一份，回来换回去，仍然共用一个模型（D15 的前半条不变）。
  - 放弃了什么：关掉 App 对局就没了；要存下来，等以后和存棋谱一起做。
- **D17 照片按页面文字的方向转正，不靠照片自带的方向**（2026-10-24）
  - 为什么：平放拍书时，手机和文档扫描都可能判错方向，倒过来的照片会把左下角的题贴到右上角。作业页上一定有字（标题、说明、题号），系统文字识别能读转了方向的字，还能给出每行字的走向。
  - 放弃了什么：多一次文字识别，在小图上约零点几秒；没有字的照片不转。
- **D18 重拍按页码和题号认出同一道题，替换不重复存**（2026-10-24）
  - 为什么：重拍多半是上次没拍好；同一道题存两份，孩子分不清做哪个。
  - 放弃了什么：家长校对过的改动会被换掉；缺页码的照片认不出是重拍，照常新存。
- **D19 找线看“比两侧暗”，不只看局部阈值**（2026-10-24）
  - 为什么：拍的时候手一晃，一个方向的线糊成浅灰色的宽带，按局部阈值它不是墨，第 34 页 6 道题只认出 2 道。把阈值放松，讲解页灰底框的边又会被当成线。线的特点是比两侧都暗，糊了也一样；灰底框的边一侧暗一侧亮，不算。
  - 放弃了什么：每页多算两张图。长线、短线改成一遍扫出来，抵掉一部分，Mac 上每页还是多约 0.1～0.2 秒。
- **D20 书缝、页边按“很长却几乎不和别的线交叉”认出来，先去掉**（2026-10-24）
  - 为什么：书缝的阴影、页边、页码下面的横杠都是长直线，会把右边一列题和隔壁页、页码连成一片，整片碰到照片边被扔掉；还会被当成棋盘最右边的一列黑子。棋盘线每格都和别的线交叉，这些线不交叉。
  - 放弃了什么：被棋子挡得只露出一小段、又碰不到别的线的棋盘线也会被去掉，靠撑大外框和补线找回来。
  - 去掉的线还用来认子：压在书缝阴影上的点不认黑子，要轮廓很完整才算白子。宁可留空让家长补，也不要认出一列假黑子。

- **D21 App 离开前台就叫停 KataGo，回来重算**（2026-10-27）
  - 为什么：iOS 不让后台的 App 用 GPU。KataGo 在后台接着算，每一步 GPU 运算都被拒绝，日志刷屏；算出来的结果可能是坏的，还会进 KataGo 的缓存。申请后台运行时间也不能用 GPU。
  - 怎么做：离开前台时取消正在做的，让引擎停下所有请求；回来以后清掉 KataGo 的缓存，从停下的那一手重新算。
  - 放弃了什么：回来以后那一手要重算，多等几秒；拉下控制中心这种很短的离开也会停。

## 8. 界面原则

改界面都要守的原则。加按钮、提示之前先对一遍。

- **横屏时，摆题面板上的原图一眼就能看到，不用往下滚动。**
  - 为什么：家长校对时一边看原图一边点棋盘改子，原图要滚动才看得到就没法对照。
  - 怎么做：原图上面的东西越少越好。新加的东西先想能不能放进已有的一行（比如“没拍全”和“已经全了”放在“原图”标题那一行），或者做成一排按钮；都不行就放到原图下面。
  - 验证：`LayoutUITests.testReferenceImageVisibleInLandscape` 用启动参数 `-samplePhotoProblem` 摆上一道带原图、标着没拍全的题，横屏检查原图和“已经全了”整个在屏幕里。改了摆题面板，跑这个测试，再装到 iPad mini 上看一眼（屏幕最小）。
- **竖屏时面板在棋盘下面要滚动，给孩子看的提示放在面板最上面**，不用滚动就能看到（`LayoutUITests.testMoveMessageVisibleWithoutScrollingInPortrait`）。
